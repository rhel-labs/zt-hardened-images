= Using Red Hat Hardened Images


[[types]]
== Available types of hardened images

There are three main categories of images provided in the collection of hardened images: runtimes, services, and tools. Each of these are built in the same fashion but provide different capabilities.  Runtimes include various languages like `java`, `python`, and `dotnet` and also have `-builder` variants to allow for complex application tasks. Services include network based applications like `caddy`, `memcached`, and `haproxy` for deploying minimal versions of common services. Tools include things like `git`, `curl`, and `jq` for running a known containerized version in an isolated manner like within a CI pipeline.

== Distroless vs distribution base images

Hardened images are what's called 'distroless' images. These styles of images are targeted builds that skip certain shells and tools typically found in standard base images. Since package managers are usually part of that missing toolset, that's how the term 'distroless' was coined.

Red Hat Hardened Images for Python come in variants.
The `default` variant is distroless — no shell, no package manager, only what the interpreter needs at runtime.
The `builder` variant adds bash, dnf, and shadow-utils for dependency installation.

Starting with the default variant shows what distroless means in practice.

== Try the Default Variant

Create a new Containerfile using the default `hi/python:3.14` runtime:

[source,bash,role=execute,subs=attributes+]
----
cat > ~/flask/Containerfile.hi << 'EOF'
# Stage 1: Hardened base image
FROM {rhhi-registry}/python:3.14 #<.>

# Switch to root from the non-root user to install dependencies
# By default, these install in /tmp/.local for the non-root user
USER root
RUN pip install flask

# Set the working directory in the container
WORKDIR /app

# Copy the application files to the target directory
# COPY always executes as root
COPY --chown=65532 app.py . #<.>

# Switch to the default non-root user for runtime
USER ${CONTAINER_DEFAULT_USER} #<.>

# Expose the port Flask will listen on
EXPOSE 8080
ENV RHHI_VARIANT=builder

# Appropriately set the stop signal for the python interpreter executed as PID 1
STOPSIGNAL SIGINT
ENTRYPOINT ["python", "./app.py"]

EOF
----
Distroless characteristics:

<.> Change our base image to the hardened `default` image
<.> Change the user in `COPY` to the provided default UID instead of adding `appuser`
<.> Reset the USER with the provided ENV variable

Let's go ahead and build the demo application on the `default` Python variant.
[source,bash,role=execute]
----
podman build -t rhhi-demo:default -f ~/flask/Containerfile.hi ~/flask
----

.*Expected output (partial):*
----
STEP 4/10: RUN pip install flask
error running container: from /usr/bin/crun creating container for [/bin/sh -c pip install flask]: executable file `/bin/sh` not found: No such file or directory
: exit status 1
Error: building at STEP "RUN pip install flask": while running runtime: exit status 1
move noted after explanation, highlight it's interfering with the build more
----
What happened here? One of the changes to 'distroless' images like our new `default` is the removal of things like shells.
Not only will this effect what can happen at runtime, but also impacts the build process.
The `RUN` step executes provided commands (here `pip install`) by passing them to a shell in the image as a command line where the previous `COPY` instructions do not. 

Without a shell, what can we do? Switch to the `builder` variant.

[NOTE]
====
This failure is deliberate to pivot to our next topic. However if you know a binary or command is available in the image, like `pip` in the python runtime, you can use the "exec form" instead of the "shell form" for `RUN` like `CMD`:

RUN ["/usr/bin/python", "-m",  "pip", "install", " flask" ]
====

== Switch to the Builder Variant

The `builder` variant adds bash and other tools specifically for build steps like this.

Edit the Containerfile and change the `FROM` to include the appropriate tag.
[TIP]
====
The `nano` and `emacs` editors are also available if you feel more comfortable with those
====
[source,bash,role=execute,subs=attributes+]
----
vi ~/flask/Containerfile.hi
----
[source,dockerfile,subs=attributes+]
----
# Stage 1: Builder base image
FROM {rhhi-registry}/python:3.14-builder #<.>
----
<.> The tagging format for `python` images is <version>-builder


[source,bash,role=execute]
----
podman build -t rhhi-demo:builder -f ~/flask/Containerfile.hi ~/flask
----

== What's in the Builder Image?

There are some other differences in the packages installed and the tools available. List the images just built. Note that the hardened image is just over half the size of the UBI based image.

[source,bash,role=execute]
----
podman images rhhi-demo
----

.*Expected output:*
----
REPOSITORY           TAG         IMAGE ID      CREATED         SIZE
localhost/rhhi-demo  builder     1d8177f35b89  48 seconds ago  195 MB
localhost/rhhi-demo  ubi         5b0d4e2582f9  11 minutes ago  263 MB
----
The new image is smaller, but we've included everything in the `builder` image in our application, including a shell that we won't want in production.

[source,bash,role=execute]
----
podman exec -it rhhi-builder /bin/sh -c 'ls -al /app'
----

The builder variant carries dnf, bash, shadow-utils, and their dependencies.
These are needed at build time to *install* Flask, but they are not needed to *run* Flask.
Shipping this image to production is about the equivalent of shipping a slightly smaller version of our UBI image.  
We get faster CVE resolution, but the size and attack surface is still larger than necessary.  
How can we ship just what we need for the runtime image to work in production?

[source,bash,role=execute]
----
podman stop rhhi-builder 
----
== The Multi-Stage Solution

Multi-stage builds allow you to separate the final application artifacts from build time components and to choose the smallest runtimes for production. 
This keeps with the overall goal of minimal images, reduced attack and risk surfaces. 
Multi-stage builds provide a good blend of flexibility and control.

This will combine the use of different variants for different purposes.

`Containerfile.hardened` separates the two concerns.
Stage one uses the builder variant to install Flask into a prefix directory.
The standard RUN command works as expected since the `builder` includes a shell.
Stage two copies only that prefix into the lean default runtime — the builder and its packages are discarded.

TIP: This is an extremely simple example for the purposes of this lab, production multi-stage builds can be much more complicated to increase isolation between build and runtime dependencies, including full compile chains that only copy final binaries.

[source,bash,role=execute]
----
cat ~/flask/Containerfile.hardened
----

[source,dockerfile]
----
include::example$flask/Containerfile.hardened[]
----
<.> Stages create intermediate images
<.> final stage doesn't get an AS, will use the tag from build command
<.> --from uses the name provided in the FROM AS combination

[source,bash,role=execute]
----
podman build -t rhhi-demo:hardened -f ~/flask/Containerfile.hardened ~/flask
----
Building this image, you'll see that `podman` creates a new image for each set of steps, delimited by the new `FROM` directive.
The `AS` in that directive let's us refer to those images in later stages.
The build output will have a new `[X/Y]` label for each step to show which stage of how many the step is in. 
This makes finding issues in longer Containerfiles with many stages easier.

podman images rhhi-demo

localhost/rhhi-demo  hardened    fbd531176581  57 seconds ago  120 MB

The multi-stage final output is smaller still.
Let's look at the RPM counts.
Our demo images set an application entrypoint, so we have to pass `--entrypoint` to run `rpm` directly instead.

[source,bash,role=execute]
----
podman run --rm --entrypoint rpm rhhi-demo:ubi -qa | wc -l
podman run --rm --entrypoint rpm rhhi-demo:builder -qa | wc -l
podman run --rm --entrypoint rpm rhhi-demo:hardened -qa
----

.*Expected output (partial):*
----
Error: crun: executable file `rpm` not found in $PATH: No such file or directory: OCI runtime attempted to invoke a command that was not found
----

The hardened image has no `rpm` and no shell — both are absent by design.
This is what distroless means in practice: the binary simply does not exist in the image.

== Looking Inside a Running Distroless Container

The `rpm` command failed because the binary was stripped from the hardened image.
That is the point of distroless — but it raises a real operational question.
If a container misbehaves in production and it has no shell, no `rpm`, and no tools,
how do you inspect it *without* rebuilding it to add those tools back?

The answer is an ephemeral _debug sidecar_: a separate, disposable container that
shares the target's process and network namespaces, brings its own tools, and
disappears when you exit. The production image never changes.

Even though the hardened image has no `rpm`, a sidecar can still answer what is
installed. Run this one-shot:

[source,bash,role=execute,subs=attributes+]
----
podman run --rm --entrypoint="" \
  --pid container:rhhi-hardened \
  --security-opt label=disable \
  --user 0 \
  {rhhi-registry}/core-runtime:latest-builder \
  rpm --root=/proc/1/root -qa | wc -l #<.>
----
<.> `--root=/proc/1/root` points `rpm` at the *target's* filesystem, not the sidecar's

.*Expected output (the exact count varies by image build):*
----
100
----

The tool the image lacks now runs from the outside, against the image's own files.
The rest of this section builds a reusable sidecar and shows how that path into the
target's filesystem works.

=== Build a Debug Sidecar

Build a small debug image once. It is never shipped with the application — it exists
only to attach to a running container when you need it.

[source,bash,role=execute,subs=attributes+]
----
cat > ~/flask/Containerfile.debug << 'EOF'
FROM {rhhi-registry}/core-runtime:latest-builder
USER root
RUN dnf -y install busybox && dnf clean all
USER 65532
CMD ["/bin/bash"]
EOF
----
The builder base carries `rpm`, `bash`, `curl`, and coreutils; `busybox` adds the
process and network inspection applets in a single package.

[source,bash,role=execute]
----
podman build -t rhhi-debug -f ~/flask/Containerfile.debug ~/flask
----

The hardened image from earlier is still running as `rhhi-hardened`. Attach an
interactive sidecar to it:

[source,bash,role=execute]
----
podman run --rm -it \
  --pid container:rhhi-hardened \
  --network container:rhhi-hardened \
  --security-opt label=disable \
  --user 0 \
  rhhi-debug bash
----

=== Reaching the App's Files

The natural first move is to list the application directory:

[source,bash,role=execute]
----
ls /app
----

.*Expected output:*
----
ls: cannot access '/app': No such file or directory
----

The sidecar shares the target's _process_ and _network_ namespaces, but each
container keeps its own _filesystem_. `/app` lives in the target, not here.

The kernel exposes every process's root filesystem at `/proc/<pid>/root`. Because
we share the PID namespace, the application is PID 1 — so `/proc/1/root` is the
target's entire filesystem, viewed from the sidecar:

[source,bash,role=execute]
----
ls -l /proc/1/root/app
----

.*Expected output:*
----
-rw-r--r--. 1 65532 65532 2224 ... app.py
----

To confirm this is the real filesystem and not just an entry showing that a file
exists somewhere, read the contents:

[source,bash,role=execute]
----
head /proc/1/root/app/app.py
----

.*Expected output (partial):*
----
import os
from flask import Flask, request, render_template_string
import hashlib
----

That is the actual source running as PID 1 — the same path the earlier `rpm --root`
command used to read the target's package database.

=== Inspecting the Running Process

The application has no tools of its own, but the sidecar does. Because `busybox`
applets may not be symlinked onto the `PATH`, first list what is available:

[source,bash,role=execute]
----
busybox --list | tr ',' ' '
----

Every name in that list is an applet you invoke as `busybox <name>`. Use it to see
the target's processes:

[source,bash,role=execute]
----
busybox ps -o pid,user,comm
----

.*Expected output (partial):*
----
    1 root     python3
----

The application is PID 1 in the shared process namespace. Now look at what it is
listening on:

[source,bash,role=execute]
----
busybox netstat -tlnp
----

.*Expected output (partial):*
----
tcp   0   0 0.0.0.0:8080   0.0.0.0:*   LISTEN   1/python3
----

The socket belongs to PID 1 — the same process. Finally, exercise the app over the
shared network namespace:

[source,bash,role=execute]
----
curl -s -o /dev/null -w "HTTP %{http_code}\n" localhost:8080/crypto-demo
----

.*Expected output:*
----
HTTP 200
----

`localhost` inside the sidecar is the target's `localhost`, so the request reaches
the app — none of which required a single tool inside the production image.

Exit the sidecar. Because it was started with `--rm`, it is gone completely, and the
hardened image is exactly as minimal as before.

[source,bash,role=execute]
----
exit
----

[NOTE]
====
For heavyweight debugging, `procps-ng`, `iproute`, and `gdb` are available in the
hummingbird repositories and can be added to the debug image the same way. The
principle holds either way: debug tools live in a disposable sidecar, never in the
shipped image.
====

AUTHOR NOTE (not rendered): possible "Going Further" addition.

A more advanced pattern adds RPMs to a distroless *runtime* image without
regressing to the builder variant and without breaking the package manifest.
Instead of COPY --from an install tree (which overwrites the base image's own
rpmdb), the final stage bind-mounts the builder ephemerally to borrow its dnf
toolchain and installs into the distroless root in place:

  RUN --mount=type=bind,from=<builder-image>,target=/builder \
      LD_LIBRARY_PATH=/builder/lib64:/builder/usr/lib64 \
      RPM_CONFIGDIR=/builder/usr/lib/rpm \
      /builder/usr/bin/dnf install -y --installroot=/ \
      --setopt=reposdir=/builder/etc/yum.repos.d <packages>

The base image's rpmdb is updated (dependencies resolved, manifest intact) and
no package manager is committed to the final image.

Judged too advanced for a hands-on step at this lab's altitude (bind mounts from
images, borrowed toolchain env, installroot/rpmdb merge semantics), and the lab's
Flask app needs no runtime RPMs to motivate it. Hold as reference only.

A blog post covering this exact concept is in draft: "Chasing Zero CVEs: Lessons
from a Real Container Build" (Pi-hole rebuilt on core-runtime). It walks the
RUN --mount install, the installroot/COPY rpmdb-overwrite failure mode, and the
grype/SBOM payoff. When it publishes, add a one-line link here (or a short
"Going Further" NOTE) pointing readers to it instead of teaching the mechanic
inline.

That same post also describes the busybox debug sidecar taught above (a
core-runtime:builder + busybox image used for `busybox --list`, `rpm -ql`, and
`dnf --assumeno install` discovery), so it could also be linked from the
"Looking Inside a Running Distroless Container" section.
